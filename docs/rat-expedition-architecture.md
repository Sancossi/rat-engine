# Rat Expedition — минимальная архитектура на rat-engine

Дата: 2026-09-08. Основание: [ADR-017](../vault/production/decisions/ADR-017%20Rat%20expedition%20uses%20rat-engine.md), [GDD](../vault/game/GDD.md), [P1](rat-expedition-traversal-spec.md). Выбор собственного движка принят пользователем; нижеследующее — технический контракт будущих срезов, **не реализованные системы**. Автор спецификации — Codex. Документ подготовлен с `gds-game-architecture`: прочитаны skill, конфигурация, проектный контекст, init и шаблон; применена проектная адаптация по уже утверждённым входам, без заявления о прохождении девяти интерактивных шагов.

## Основа и границы

Продолжаем этот репозиторий, без нового движка с нуля и без переноса в Godot/Unity. Базовая версия CMake — `0.1.0`, язык C++20, исходный проверенный baseline `ecb6fbf84dc06b0ebd87bc40ed86caea192eeee2`. Это идентификатор разработки, не обещание стабильного production-релиза. Предыдущая приёмка baseline: 714 CTest-проверок и 16 Python-тестов; игровые требования экспедиции ими ещё не доказаны.

Сохраняем закреплённые зависимости `cmake/Dependencies.cmake`: bgfx.cmake `v1.129.8940-496`, GLFW `3.4`, ImGui `v1.91.8-docking`, nlohmann/json `v3.11.3`, miniaudio `0.11.25`, Catch2 `v3.7.1`. Не обновлять их попутно. На Windows существующий Auto backend выбирает D3D11; фактический адаптер записывается из запущенного приложения, не выводится из списка установленного оборудования.

| Подсистема | Что уже существует | Что предстоит сделать |
| --- | --- | --- |
| Симуляция | `SimulationSession`, fixed tick 1/120 с, `PlayerBody`, лестницы, поверхности/коллизии | Игровая стойка/низкий лаз, координация двух сцен, безопасное восстановление P1 |
| Представление | `GreyboxScene` рисует геометрию; `Renderer` управляет bgfx/кадром; `RenderWorld` содержит packets | Дисковый PNG и настоящая отрисовка спрайта, анимация, перекрытия P1. `Renderer::submit` пока маркирует packets, не рисует их меши |
| Authoring | `MapDocument` → compiled runtime map; редактор, undo/redo, JSON | Две новые карты и небольшие игровые метаданные; без универсального редактора RPG |
| Состояние | `GameState`: switches/variables/items/self-switches, событие/текст | Правила предметов P2, квест/выборы P3, партия/бой P4; не выдавать текстовое событие за готовую систему диалоговых выборов |
| Хранение | Строгое schema 2, транзакционное чтение, атомарная замена `FileStore` | Отдельный игровой слот, полное состояние экспедиции и отказ от чужого формата P5 |
| Выпуск | Release-редактор, install/CPack ZIP, executable-adjacent data | Отдельное игровое приложение/пакет P1, запуск без editor UI и исходного checkout |

Фактические библиотеки: `rat_core`, `rat_engine`, `rat_editor_logic`, `rat_editor_app`; приложения `rat-editor`, тесты `rat_tests`. Runtime и authoring остаются в `rat_core`. Публичный `rat_core` содержит только переносимые типы и JSON; не добавлять bgfx/GLFW/Win32. `rat_engine` уже связывает bgfx публично: это существующая граница графического адаптера, не свойство ядра.

## Размещение и зависимости будущего P1

- `apps/game/`: будущий executable target `rat-game`, окно/ввод, игровой coordinator и минимальные пауза/подсказка. Пока такого target нет. Он приватно связывает `rat::engine`, GLFW и ImGui для временного UI; не связывает `rat::editor_app` и панели.
- `src/game/expedition/`: переносимые правила и `ExpeditionSession`; первоначально эти исходники непосредственно включаются в `rat-game` и отдельный headless test target. Не вводить библиотеку/фреймворк до необходимости; тестовая сборка этих исходников связывает только `rat::core` и Catch2.
- `src/engine/`: только необходимые общие additions: GPU sprite adapter и возможность скрыть стандартную фигуру игрока/отдельные стены при отрисовке greybox. Не переделывать всё представление или ECS.
- `data/expedition/`: выпускаемые новые maps, scene metadata, sprites, manifest; `assets/expedition/`: редактируемые исходники и `credits.json` (source, author/tool, license/terms, modifications, exported path для каждого ассета). Эти каталоги будут созданы в P1. Старые `data/maps/*` сохраняются.
- Узкие platform helpers окна и путей, необходимые обеим программам, перенести из `apps/editor/platform/` в `apps/platform/` с обновлением include/source references и прежними editor-тестами. Не переносить coordinator/panels в игровое приложение. Создание нового platform target не требуется.

В CMake P1 добавить `RAT_BUILD_GAME` (по умолчанию OFF, ON в игровом preset) и target/data-copy/install для игры. GLFW/ImGui нужны при любой frontend-сборке; miniaudio пока нужен прежнему editor, игре P1 звук не обязателен. Сохранить renderer-OFF headless режим, link-isolation и обычный `dev-release` редактор. Добавить `game-release` configure/build/test presets на существующем toolchain с renderer/game/tests ON, editor/gui-tests OFF, binary dir `build/game-release`.

## Состояние и поток данных

`GLFW input → game input gating → ExpeditionSession → SimulationSession tick → неизменяемый снимок представления → GreyboxScene + SpriteRenderer + UI → bgfx frame`.

`ExpeditionSession` владеет одной активной `SimulationSession`, id сцены, стойкой, точкой восстановления, визуальным следованием двух спутников и режимом Explore/Paused (Dialogue/Battle добавляются в P3/P4). Единственный источник координат лидера — `SimulationSession::player()`. Спрайты и UI не изменяют правила игры; спутники P1 не имеют коллайдеров или отдельного AI/pathfinding. Следование вычисляется из истории устойчивых положений лидера, при переходе/восстановлении вся история сбрасывается к безопасной точке.

На смене сцены coordinator загружает map+metadata в кандидат, проверяет ссылки/выход, создаёт новую `SimulationSession`, устанавливает spawn и только после успеха заменяет активный экземпляр. Ошибка оставляет старую сцену и прогресс. `SimulationSession::load` переинициализирует jump/tick/input/event runtime и меняет map/позицию; существующий `TransferPlayer` отвергает другой map id. Поэтому не использовать его как готовую межкартовую загрузку и не вызывать `apply_loaded_game` с прежним map id.

В P1 переносится только текущее traversal-состояние; карты не содержат игровых событий с прогрессом. С P2 общий инвентарь/ресурсы, с P3 квест/обещания и map-local последствия принадлежат `ExpeditionSession`, а не GPU или виджетам. Связанные события обращаются к одному состоянию через явные команды; не вести независимые копии одного ресурса в UI и `GameState`. Карточки P2–P5 определяют минимальные расширения по своим правилам, без полной RPG-схемы заранее.

Authoring: новые геометрические карты редактируются существующим editor и сохраняются новым именем; метаданные P1 редактируются в JSON с валидатором. Импорт/компиляция проверяются до замены активного мира. Для P1 достаточно перезапуска игры после правки; edit-in-playmode не является обязательной игровой функцией.

Хранение P5: отдельный `%LOCALAPPDATA%/RatExpedition/` (тестовый override через `--user-data-dir`), без чтения/записи старых editor save-файлов. Снимок содержит scene/spawn, состояние партии/квестов/предметов и изменения всех посещённых карт. Сначала полностью прочитать/проверить снимок и подготовить сцену-кандидат, затем применить одной транзакцией; запись через временный файл и атомарную замену `FileStore`. Версия игрового формата и точная schema фиксируются в P5; не переименовывать старое schema 2 в готовый формат экспедиции. P1 слота не создаёт и сохраняет только диагностику.

## Доставка, проверки и границы роста

P1 поставляет `build/game-release/apps/game/rat-game.exe` и ZIP `build/game-release/rat-expedition-0.1.0-Windows-x64.zip`: executable, только требуемые runtime DLL, `data/expedition/`, используемый шрифт и licenses/credits. CPack существующего редактора остаётся работоспособным. Данные разрешаются относительно executable, пользовательские записи — отдельно; запуск из другого working directory обязателен. Отсутствующий map/PNG даёт читаемую ошибку и ненулевой exit code при старте; при переходе сохраняет текущую сцену и показывает отказ. Платные пакеты, сеть, сервисы, телеметрия и автообновления не нужны.

Точечные headless tests проверяют стойку/потолок, границы переходов и rollback, input gating; реальный Windows-проход проверяет изображение/управление и извлечённый ZIP. Журнал включает commit, конфигурацию, renderer/adapter, путь к артефакту, сценарий и фактические результаты. Не переносить baseline test count на новую реализацию без запуска.

Если P1 не проходит выпуск без checkout, спрайт/перекрытия, лаз или безопасный подъём, остановить рост контента и зафиксировать конкретный блокер. Сначала ограниченный исправляющий срез в текущем движке; смена технологии или расширение универсальных систем требует нового решения с пользователем. Предпочтение собственного движка не отменяет критериев игрового результата. Не начинать P2 или старую очередь при незакрытом P1.

Рабочая машина (CIM, 2026-09-08): Windows 11 Pro `10.0.26200` x64; Ryzen 9 9950X3D, 16 ядер/32 потока; 125,4 GiB RAM; NVIDIA RTX 4090, driver `32.0.16.1664`; встроенная AMD Radeon, driver `32.0.13066.12`. Это инвентаризация доступного ПК, **не** фактический render adapter, замер FPS или минимальные требования. В P1 записать FPS/frame times на маршруте; целевые бюджеты A7 остаются гипотезой до проверки.
