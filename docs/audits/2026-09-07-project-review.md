# Ревизия rat-engine — 2026-09-07

База: `7be588d`, ветка `feat/sprint-4`, рабочие изменения пользователя сохранены. Проверены код ядра и редактора, CMake/CI, тесты, схемы, текущие карточки и инструкции. Это ревизия с выборочными исполняемыми проверками, а не доказательство отсутствия других ошибок.

Полная Release-сборка через VS 18 BuildTools: `ninja: no work to do`. После неё CTest: **643/643**, 5.12 с. Чистый configure с нуля, Linux, GUI, GPU-профилирование и аварийное отключение диска не проверялись. Удалённый статус GitHub Actions не проверялся. Исходники движка не изменялись.

Общий вывод: хорошая тестируемая основа прототипа, но надёжность авторского цикла и достоверность диагностики отстают от возможностей редактора. Следующий этап лучше посвятить целостности данных, воспроизводимости и рабочим инструкциям.

## Подтверждённые дефекты и риски

Приоритет P1 — исправить до активного создания контента; P2 — следующий этап стабилизации; P3 — улучшения процесса. Воспроизведения API приведены в [probe.cpp](2026-09-07-probe.cpp). Они демонстрируют существующее поведение и ещё не являются регрессионными тестами исправлений.

Повторить из корня репозитория в **x64 Native Tools / Developer Command Prompt**, после Release-сборки:

```bat
cl /nologo /std:c++20 /EHsc /MD /I src\engine\include /I apps\editor docs\audits\2026-09-07-probe.cpp /Fo:build\audit-probe.obj /Fe:build\audit-probe.exe /link build\apps\editor\rat_editor_logic.lib build\src\engine\rat_core.lib
build\audit-probe.exe
```

Ключевой фактический вывод: `header_only_save_accepted=1`, `nan_save_accepted=1`, `spaced_item_save_roundtrip=0`, `nan_tile_compile_ok=1 serialize_ok=1 reload_ok=0`, `duplicate_event_placed=1 compile_ok=0`, `undo_to_saved_still_dirty=1`, `empty_replay_accepted=1`, `future_replay_accepted=1`, `npc_positions_differ=1 npc_checksum_equal=1`, `transfer_state_map=other runtime_map=from`.

### A01 · P1 · Несохранённая карта теряется при reload/выходе

По коду: `EditorApp::hot_apply_map_path` вызывает `document_.load`, а тот очищает history и dirty. F5, Load и Reload вызывают этот путь без проверки dirty; цикл приложения завершает работу при `host_.should_close()`. В `editor_app.cpp` нет использования `document_.dirty()`.

Сценарий для ручной проверки: Edit → изменить карту → F5 либо закрыть окно → правки потеряны, undo недоступен. GUI-сценарий в этой ревизии не запускался; отсутствие защиты подтверждено чтением веток кода.

Источники: `apps/editor/editor_app.cpp:252,278,569,906,1059`; `apps/editor/editor_document.cpp:47`.
Исправление: единый маршрут закрытия/перезагрузки с Save / Discard / Cancel, индикация несохранённого документа, тест переходов. При неудаче Save действие не продолжать.

### A02 · P1 · Запись карты и save slot не атомарна

`OsFileStore::write` открывает конечный файл с `std::ios::trunc`, затем пишет и flush. Если запись оборвётся, старая версия уже уничтожена. Этим путём пользуются и `save_game`, и `save_map_to_file`.

Источник: `src/engine/src/file_store.cpp:54`; вызовы в `save_game.cpp` и `map_loader.cpp:1097`.
Это подтверждённый риск реализации, а не воспроизведённая потеря пользовательского файла. Нужны временный файл рядом с целевым, проверка завершения записи, корректная замена на Windows/Linux и тест отказа до замены. Определить требования к backup и crash durability отдельно.

### A03 · P1 · Повреждённые сохранения принимаются за корректные

Probe: `RATSAVE1\n` принимается; `pos nan 0 0` принимается и даёт NaN в позиции. `apply_loaded_game` не запрещает пустой map_id и неконечные координаты. Усечённый до заголовка файл способен заменить прогресс пустым состоянием; NaN может попасть в симуляцию.

Ещё одна несогласованность контракта: `add_item("rusty cog", 1)` и сохранение успешны, но обратная загрузка проваливается: текстовый формат не экранирует ID с пробелами. Текущий контент с underscore это не затрагивает.

Источники: `src/engine/src/game_state.cpp:25,127,148`; `src/engine/src/simulation_session.cpp:41`.
Нужны обязательные поля, finite-check, явная политика допустимых ID/экранирования, проверка полных записей и сохранение прежнего состояния при ошибке. Файловая обёртка уже разбирает во временный GameState — этот полезный контракт сохранить.

### A04 · P1 · Валидация карты пропускает NaN

Probe: карта с `tile_size=quiet_NaN()` проходит `compile_map_data`; сериализация возвращает успех, повторная загрузка собственного JSON — ошибку. Проверка `tile_size <= 0` не отсекает NaN. Это проверено для программного MapData, не заявляется как воспроизведение ввода NaN через GUI или стандартный JSON.

Источник: `src/engine/src/map_document.cpp:260`. Нужны `isfinite` и ограничения диапазона для всех геометрических чисел, согласованные между parse, semantic validation и edit API. Добавить контракт compile → serialize → load для допустимых данных.

### A05 · P1 · Новое событие может получить занятый ID

Все три места создания строят `stub_` + счётчик. После нового запуска счётчик равен 1 и не сканирует загруженную карту. Probe: добавление второго `stub_1` успешно применяется в EditorDocument, но компиляция карты затем отклоняет duplicate ID.

Источники: `apps/editor/panels/event_panel.cpp:24`, `apps/editor/editor_app.cpp:779,1230`, `apps/editor/panels/event_panel.hpp:14`.
Сценарий: создать stub_1 → сохранить → перезапустить → Add event. Нужен общий allocator; `allocate_unique_event_id` уже существует в `event_edit.cpp`. Все UI-пути должны пользоваться им. Проверка редактирования должна возвращать видимую ошибку, если инвариант всё же нарушен.

### A06 · P1 · Transfer Player рассинхронизирует карту

Probe: autorun из карты `from` выполняет transfer в `other`; после tick `state.map_id=other`, но `events.map.id=from`. Геометрия и события остаются прежними. Карта назначения не загружается и недоступный ID не отклоняется. Последующее сохранение получает ID другой карты.

Источники: `src/engine/src/event_runtime.cpp:451`; `src/engine/src/simulation_session.cpp:222`.
Решение для текущего slice: явно запретить межкартовый transfer с понятной диагностикой. Полный переход требует resolver карты, атомарной замены runtime и определения области self-switches. Не расширять scope до многокартового мира только ради закрытия дефекта.

### A07 · P2 · Replay checksum не видит перемещение NPC

Probe: два валидных runtime с одинаковым map ID, но маршрутами east/west; после одного tick позиции NPC различаются, а checksum одинаков. `runtime_checksum` не включает event overlays; `mix_interpreter` пропускает имеющийся `route_index`. Поэтому checksum не является полной проверкой существенного runtime-состояния.

Источники: `src/engine/src/replay.cpp:80,184`; `event_runtime.hpp:44,51`; `event_runtime.cpp:801`.
Добавить overlay tile/position/facing, продвижение маршрута и явный контракт полного состояния VM. В replay header нужен fingerprint содержимого карты/версии runtime, если запись должна переживать правки карты. Probe намеренно использует различающееся содержимое карты: он доказывает слепую зону, а не недетерминизм одной карты.

### A08 · P2 · Replay недостаточно проверяет формат

Probe: `{}` и `{"schema_version":999,"ticks":[]}` успешно читаются. `load_recording` подставляет значения по умолчанию, неизвестная версия не отклоняется. `replay_input_sequence` создаёт сессию с default dt, не используя `header.dt`, и не сверяет map_id.

Источники: `src/engine/src/replay.cpp:153,296,323`.
Нужны строгая версия, обязательные поля, положительный конечный dt, политика map identity, последовательность ticks, отдельный результат ошибки. Нулевые checksum/tick_id сейчас отключают часть сравнений — этот режим следует обозначить явно, чтобы отсутствие доказательства не выглядело успешной проверкой.

### A09 · P2 · Dirty не отражает возвращение к сохранённому документу

Probe: mark_clean → move → undo остаётся dirty. Повторная compile_graphs_for_apply без изменения графа также помечает документ dirty.

Источник: `apps/editor/editor_document.cpp:35,59,118`.
Пока UI игнорирует dirty, симптом мало заметен; после A01 появятся ложные запросы сохранения. Нужен clean checkpoint истории либо сравнение канонического содержимого, отдельно от revision производных данных.

### A10 · P2 · Event touch описан как доступный, но не реализован

`vault/game/Event System.md:29` и схема перечисляют Event touch. В `EventRuntime::why_not_fired` он безусловно возвращает WrongPage; исполняемого пути для этого trigger в runtime не найдено. Это разрыв между опубликованным набором возможностей и реализацией, не требование срочно расширять MVP.

Нужно пометить trigger unsupported и отклонять/предупреждать при authoring либо отдельно запланировать семантику движущегося события. Приёмка: автор не может создать молча неработающее событие.

## Документация и организация работы

### A11 · P1 для работы с базой знаний · Ссылки на заголовки вместо файлов

В исходных 226 markdown-заметках простой сканер нашёл **121 уникальную цель**, не совпадающую с именем markdown-файла; 117 совпадают с H1 существующих заметок. `aliases:` не найден. Число — кандидаты статической проверки, не результат UI-обхода всех ссылок.

Конкретный пример: `[[feat: Mouse viewport map edit]]` ведёт по имени заголовка, а файл называется `feat-mouse-viewport-map-edit.md`. Правильная переносимая форма — `[[feat-mouse-viewport-map-edit|feat: Mouse viewport map edit]]`. В локальном obsidian-vault SKILL ошибочно предлагается использовать heading/filename как взаимозаменяемые цели.

По [документации Obsidian](https://obsidian.md/help/links), ссылка на заголовок другой заметки должна содержать имя заметки и `#`; H1 не заменяет имя файла. [Aliases](https://obsidian.md/help/aliases) позволяют удобный поиск, но генерируемая ссылка всё равно содержит реальную цель.

Исправлять по однозначной карте H1 → путь, с отчётом неоднозначных целей; не создавать новые пустые файлы по ошибочным названиям. Добавить проверку ссылок в CI. В этой ревизии существующие ссылки не переписывались.

### A12 · P2 · Планирование не имеет согласованного состояния между спринтами

Четыре незакрытых follow-up прикреплены к нему, но вынесены за порядок завершённого спринта. Нужно определить допустимое состояние «между спринтами» либо назначить следующий спринт и перенести очередь явно.

Это не означает, что Sprint 14 закрыт неправомерно: его итог явно отделяет polish. Однако `chore-ramp-voxel-review-polish.md` содержит функциональный симптом неверного yaw при размещении по боковой грани; название «polish» занижает важность для автора карты.

Уже учтённые карточки, не дублировать: `chore-{bridge-climb-review-test,occupancy-review-test,edit-voxel-review,ramp-voxel-review}-polish.md`; открытый `event-graph-self-pin-drag-stays-armed.md`.

### A13 · P2 · Карта архитектуры и статусы отстают от кода

Заявленная целевая нарезка `rat_authoring/rat_runtime/rat_render/rat_assets` не совпадает с текущими targets. Нужны короткий «как проект устроен сейчас», таблица implemented/partial/planned, актуальные hotkeys и ограничения. Отдельно различать AssetRegistry/GPU-stub и готовый импорт mesh/material/texture.

### A15 · P2 · Проверки не покрывают наиболее дорогие отказы

CI собирает Release на Windows/Linux и запускает headless Catch2; это полезная база. Но в workflow нет Debug/sanitizer job, статического анализа, GUI smoke, теста переносимого пакета, лимита времени CTest и проверок vault. 643 теста проходят одновременно с A03–A09: количество тестов не заменяет негативные контракты.

Добавить по порядку: регрессии найденных дефектов; Linux ASan/UBSan; ограничение времени; детерминированный desktop smoke и проверку save/reload; валидацию ссылок и статусов. Не добавлять бессодержательные тесты ради покрытия строк. Smoke сейчас дублируется отдельным шагом после общего CTest — низкий приоритет.

### A16 · P2/P3 · Среда сборки и распространение требуют ручных знаний

В обычном PowerShell cmake/ctest/gh не найдены в PATH. VS build environment доступен и полная сборка работает через VsDevCmd. Первый python в PATH — WindowsApps alias, который не запустился в sandbox; каталог навыков прочитан при разрешённом сетевом запуске. Нужны обнаружение toolchain через vswhere и документированный script/preset, а не абсолютный путь к локальной версии VS.

`RAT_DATA_DIR` зашит абсолютным путём в source tree (`apps/editor/CMakeLists.txt:85`), карта grey_yard выбирается в коде; save slot зависит от cwd. Переносимость exe без репозитория не обеспечена этим контрактом. Нужны project/data root и writable user-data root перед раздачей билда тестерам.

`cmake/Dependencies.cmake` безусловно получает bgfx/GLFW/ImGui; `RAT_BUILD_EDITOR=OFF` не делает configure чисто headless. Сборка rat_core не линкует их, но конфигурация всё равно требует зависимости. Разделить opt-in графики и тесты минимальной конфигурации, когда это станет частью поддерживаемого workflow.

## Пробелы, которые пока не являются багами

- Desktop-приёмка: нет проверенного в этом проходе набора кадров для камер, рамп, мостов, шрифтов и event graph. Нужны фиксированные camera poses, разрешения/DPI и перечень контрольных действий.
- Производительность: есть frame metrics, но не найден отдельный benchmark-набор с бюджетами. Перед broadphase/object pool измерить размер карты, количество occupancy/NPC, tick p95/p99, время bake/apply и память undo. Полные копии MapData в editor и elevation snapshots заслуживают измерения, не немедленной оптимизации.
- Крупные точки изменений: editor_app.cpp — 1362 строк, map_loader.cpp — 1116, player_jump.cpp — 1078, event_runtime.cpp — 1039, event_graph_canvas.cpp — 858. Размер сам по себе не дефект; выделять операции сохранения/переходов/редактирования по тестируемым контрактам при исправлениях.
- Content pipeline: data содержит audio/fonts/maps; источник художественных assets в Art Direction пока TBD. Регистрация ресурсов не равна готовому mesh import и процедурной анимации. Нужны минимальный исходный asset, экспортный формат, масштаб/pivot и проверенный путь до отображения — когда выберем художественный этап.
- Product decisions: Art Direction содержит незакрытые checkbox с уже вписанными «нет»/«да», а GDD всё ещё оставляет день/ночь вопросом. Зафиксировать решение и границы следующего playable; не добавлять field physics, ECS или новый renderer по инерции.

Мне для более надёжной работы не хватает прежде всего исполняемых контрактов и доступной диагностики: одной команды проверки проекта, воспроизводимого desktop-сценария, полного checksum, согласованных инструкций и утверждённого следующего результата. GitHub-плагин не нужен для локальной ревизии; доступ к Actions понадобится при разборе реальных удалённых падений.

## Предлагаемая очередь

1. A11/A12/A14: восстановить навигацию и однозначные правила; выбрать следующий спринт без автоматического запуска всего backlog.
2. A01–A05/A09: защита авторской работы, атомарная запись, валидация и уникальность ID; регрессии на каждый конкретный дефект.
3. A06: до реализации resolver запретить неподдерживаемые межкартовые переходы.
4. A07/A08/A10: достоверный replay и честный список поддерживаемых событий.
5. A15/A16: негативные проверки, sanitizer, повторяемая сборка и desktop smoke. Затем вернуться к известным рампам/мосту и выбранному контентному этапу.

Этот документ не запускает реализацию очереди. Карточка продолжения: [project-audit-followups](../../vault/production/tasks/project-audit-followups.md). Существующие чужие изменения, статусы старых спринтов и исходники оставлены как были.
