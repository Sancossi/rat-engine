# ADR-017 — Rat Expedition продолжает собственный rat-engine

## Контекст

После подготовки концепции пользователь 2026-09-08 поручил перейти к следующему этапу и указал предпочтение собственного движка: «Давай приступим к нему но я бы хотел свой движдок». В контексте [[expedition-engine-decision]] это выбор собственного движка; используем уже существующий rat-engine в текущем репозитории. Автор выбора — пользователь bogor, техническую фиксацию подготовил Codex.

[Сравнение](../../../docs/rat-expedition-engine-comparison.md) раньше рекомендовало Godot по ожидаемой стоимости готового sprite/editor pipeline. Эта рекомендация сохраняется как история исследования, а не действующее решение. Unity также рассматривалась; преимуществ, достаточных для переноса с учётом предпочтения пользователя, не установлено. Три runtime-прототипа не строились; сравнительные скорости разработки не измерялись.

## Решение

Продолжать **rat-engine 0.1.0 / C++20**, baseline `ecb6fbf84dc06b0ebd87bc40ed86caea192eeee2`. Версия взята из CMake, baseline из проверенного закрытия подготовки; это не stable production release. Сохранить закреплённые зависимости, CMake, редактор, тесты и полезные инструменты. Игру разместить в том же репозитории: будущий `rat-game`, игровые правила `src/game/expedition/`, новые выпускаемые данные `data/expedition/`, исходники ассетов `assets/expedition/`. Графика/платформа остаются вне public `rat_core`; предполагаемое разделение библиотек старого roadmap не активируется.

Принять [минимальную архитектуру](../../../docs/rat-expedition-architecture.md) как контракт следующих срезов и [P1 specification](../../../docs/rat-expedition-traversal-spec.md) как уточнение существующей [[expedition-prototype-traversal]]. Старые карты, сохранения, пользовательские изменения и закрытые этапы сохраняются; автоматической миграции нет. Runtime начинается только в P1 после закрытия E1 и планирования следующего спринта.

## Последствия и критерий пересмотра

Переиспользуем fixed-tick simulation, поверхности/лестницы, JSON, editor authoring и FileStore. Недостающие P1 системы: настоящий дисковый sprite renderer, стойка с clearance, game scene coordinator, читаемые перекрытия и самостоятельный Windows-пакет. Квесты, партия/пошаговый бой, полное игровое сохранение и производство контента ещё предстоят в P2–P5/E3; кодовая основа не означает готовую RPG.

Мы принимаем дополнительную стоимость обслуживания собственного стека ради предпочтения пользователя. Если P1 не проходит экспорт без checkout, спрайт/лаз/лестницу/перекрытия, остановить рост контента и исправить ограниченный блокер; при невозможности уложиться в малую игровую задачу вынести новое решение пользователю. Godot не становится автоматическим fallback, срок разработки не обещан.

Доступный Windows ПК и пределы измерений зафиксированы в архитектуре. GUI/производительность экспедиции этим ADR не проверены; приёмка E1 находится в карточке решения, P1 потребует реальный игровой проход.
